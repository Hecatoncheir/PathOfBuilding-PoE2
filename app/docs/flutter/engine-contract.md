# Контракт движка: первая версия

Статус: минимальный экспериментальный сервер реализован в `app/tools/headless_server.lua`; Flutter-клиент ещё не реализован. Проверенный способ запуска Windows — Python/ctypes с имеющейся LuaJIT DLL; Python здесь экспериментальный загрузчик, а не обязательная зависимость конечного приложения.

Запуск сервера: `python app/tools/run_headless.py app/tools/headless_server.lua`. Проверка транспорта: `python app/tools/check_engine_protocol.py`. Проверены 10 сообщений: неверный JSON, инициализация, загрузка эталона, изменение модификаторов, устаревшая ревизия, экспорт, неверный XML, сохранение состояния после ошибки, неизвестная команда и завершение. Диагностика wrapper направлена в stderr. Полноценная отмена вычислений, жёсткое ограничение выделения памяти при чтении строки, восстановление после аварии и глубокая проверка произвольного XML ещё не реализованы.

## Транспорт

Для первого desktop-эксперимента использовать отдельный процесс и JSON Lines через stdin/stdout. Один запрос и ответ занимают одну строку; XML передаётся экранированной JSON-строкой. Диагностика должна идти в stderr: существующий wrapper печатает сообщения загрузки, поэтому до подключения клиента нужно разделить потоки.

Процесс обслуживает одну открытую сборку и последовательно выполняет команды. Ограничить размер сообщений и время ожидания; при сбое восстановить последний подтверждённый XML. Не открывать сетевой порт и не исполнять произвольный Lua из клиента.

## Конверты

Запрос:

```json
{"protocol":1,"id":"request-1","method":"loadBuild","params":{"xml":"<PathOfBuilding2>...</PathOfBuilding2>"}}
```

Успешный ответ:

```json
{"protocol":1,"id":"request-1","revision":1,"result":{"targetVersion":"0_1","treeVersion":"0_5"}}
```

Ошибка:

```json
{"protocol":1,"id":"request-1","error":{"code":"INVALID_BUILD","message":"Не удалось открыть сборку","recoverable":true}}
```

Числа и версии в примерах описывают форму сообщения; ответ всегда формируется из движка.

## Минимальные команды

| Команда | Параметры | Результат | Условие |
| --- | --- | --- | --- |
| initialize | protocol | Версия протокола, движка и доступные команды | До открытия сборки |
| loadBuild | xml | Версии и новая ревизия | Проверить XML до замены текущего состояния |
| getSnapshot | revision | Выбранные параметры и разрешённые показатели | Проверить ревизию |
| setCustomMods | revision, text | Новая ревизия и пересчитанные показатели | Только существующий редактор модификаторов |
| exportBuild | revision | XML | Использовать SaveDB, сохранять неизвестные поля согласно проверкам |
| shutdown | — | Подтверждение | Завершить процесс и освободить runtime |

Сначала поддержать проверенный сценарий Fireball. Команды дерева, предметов, камней, наборов, группы, сравнения и источников добавлять по реестру функций; не заявлять их готовыми заранее.

## Согласованность и ошибки

- Ревизия увеличивается только после успешной загрузки или изменения. Запрос с устаревшей ревизией получает `STALE_REVISION`.
- Клиент связывает ответ с `id`; результат старого запроса не заменяет текущую сборку.
- Не сериализовать весь `mainEnv`: там есть ссылки и внутренние объекты. Использовать явный перечень полей результата.
- Отсутствующие показатели передавать как отсутствующие/`null` с описанным смыслом, не подменять нулём. `NaN` и бесконечность — ошибка расчёта.
- Минимальные ошибки: `INVALID_REQUEST`, `UNSUPPORTED_PROTOCOL`, `UNKNOWN_METHOD`, `INVALID_BUILD`, `STALE_REVISION`, `CALCULATION_FAILED`.
- Историю undo/redo реализовать в одном владельце. До полноценного журнала команд эксперимент может восстанавливать XML-снимок; это не обещание окончательной архитектуры.
- Изменение, завершившееся ошибкой, должно возвращать сборку в последнее подтверждённое состояние. Проверить отдельно до использования UI.

## Критерии проверки транспорта

Открытие эталона; изменение модификатора; совпадение расчётов; экспорт и повторная загрузка; неверный JSON/XML; неизвестная команда; устаревшая ревизия; превышение лимита; аварийное завершение. Диагностические сообщения не должны повреждать JSON-поток. Независимая команда `python app/tools/run_headless.py app/tools/check_headless_baseline.lua` проверяет расчётную основу без перезаписи эталонов.

## Сведения о сборке и выбор умения

`getSnapshot` возвращает `buildInfo`: `name`, `level`, `class`, `ascendancy`, `groups`, `skills`. Каждый список содержит `entries` с `id` и `label`, `selected` и `enabled`; значения берутся из оригинальных контролов `Build.lua`.

`selectMainSkill` принимает `{control: "groups" | "skills", id: integer}` и текущую ревизию. Команда проверяет доступность Lua-контрола, вызывает его `SetSel`, запускает исходный `OnFrame` и возвращает обновлённый снимок. Выбор входит в историю XML. Названия очищаются только от цветовых кодов Lua. Остальные варианты основного умения пока не поддержаны.
