# Эталонные данные и запуск без интерфейса

## Найденная основа

- `src/HeadlessWrapper.lua` определяет запуск без окна, загружает `_SimpleGraphic.def.lua` и `Launch.lua`, вызывает `OnInit`/`OnFrame` и предоставляет `newBuild`, `loadBuildFromXML`, `loadBuildFromJSON`.
- `build.calcsTab.mainOutput` и `build.calcsTab.mainEnv` используются существующими расчётными тестами как источники результатов.
- `.busted` задаёт helper `HeadlessWrapper.lua`, рабочую директорию `src`, путь к библиотекам `runtime/lua` и исключение тега `builds`.
- `.github/workflows/test.yml` запускает системные тесты через Busted/LuaJIT в контейнере проекта. Проверку ModCache выполняет отдельно.

Это хорошая стартовая точка для адаптера, но не готовый независимый движок: wrapper создаёт существующие UI-модули и использует кадр как точку пересчёта. Нужно проверить зависимости от графических заглушек, файловых путей и нативных библиотек.

## Состояние локальной проверки

Обновление: через `app/tools/run_headless.py` успешно запущен имеющийся Windows `runtime/lua51.dll`. Проверены создание сборки, расчёт Fireball, удвоение урона пользовательским модификатором и загрузка XML с возвратом исходных показателей. [Первый эталон](fixtures/fireball-basic/README.md) содержит исходный XML, нормализованный XML и результаты. Это отдельный эксперимент, а не запуск Busted. Установка дополнительных пакетов теперь разрешена пользователем, но для этого эксперимента не потребовалась.

При подготовке документов команды `lua`, `luajit` и `busted` не обнаружены в PATH. В `runtime` есть `lua51.dll` и библиотеки приложения, но это не подтверждает наличие самостоятельного интерпретатора или запуска Busted. Системные Lua-тесты пока не запускались. Новые пакеты и контейнеры не устанавливались.

Команда из существующего CI для одного теста: `busted --lua=luajit ../spec/System/TestOffence_spec.lua` с конфигурацией `.busted` из корня проекта. Перед локальным запуском проверить обработку рабочей директории установленной версией Busted. Не считать команду проверенной на текущем Windows-окружении.

## Формат будущего снимка

Для каждого эталона хранить `build.xml`, `expected.json` и описание воспроизведения. В метаданных указывать Git SHA, версии дерева/данных/движка, выбранные наборы и умение, условия боя и перечень показателей. Не сохранять токены, аккаунты или случайные абсолютные пути.

- Идентификаторы, выбранные узлы, слоты, настройки и строки сравнивать строго.
- Для чисел согласовать абсолютный и относительный допуски отдельно по каждому показателю после изучения существующих проверок. Не задавать универсальный допуск, который скроет регрессию.
- `NaN`, бесконечность и отсутствующее поле считать ошибкой, если эталон явно не разрешает такой результат.
- После записи XML открыть его повторно и сравнить смысловые данные и расчёты; побайтовое совпадение XML не обязательно из-за форматирования.
- Снимать результаты только после завершения пересчёта соответствующей ревизии; не сериализовать целиком циклические объекты `mainEnv`.

## Следующий технический эксперимент

1. Найти доступный локальный способ запуска wrapper без установки зависимостей.
2. Запустить существующий небольшой расчётный тест и проверить повторяемость.
3. Получить XML и результаты одной сборки через существующий код сохранения.
4. Повторить загрузку/изменение/пересчёт/экспорт в отдельном процессе.
5. Описать ограничения и только затем проектировать протокол Flutter ↔ Lua.
